Read the uploaded PDF, `STEMPath_Finder_Claude_Code_Project_Brief.pdf`, and use it as the main source of truth for this project.

Build a working MVP for **STEMPath Finder / OpportunityRadar AI**, a web application that helps middle-school and high-school students find verified STEM opportunities.

Before writing code, briefly summarize:

1. The problem the app solves
2. The smallest useful MVP
3. The technology stack you will use
4. The database structure
5. The pages and features you will build

Then build the MVP described below.

## MVP Goal

Students should be able to complete a simple form and receive ranked STEM opportunities based on eligibility, interest, location, cost, experience level, time commitment, and deadline.

Administrators should be able to review, approve, reject, edit, publish, and unpublish opportunities.

Do not attempt to build every future feature described in the PDF.

## Required Pages

Create:

1. Homepage
2. Opportunity matching form
3. Matching results page
4. Opportunity detail page
5. Private admin dashboard
6. Candidate opportunity review queue

## Student Matching Form

Ask the student for:

* Grade
* Age
* STEM interest
* Opportunity type
* Location preference
* Remote or in-person preference
* Cost preference
* Experience level
* Time commitment

## Opportunity Database Fields

Each published opportunity should support:

* Name
* Organization
* Category
* STEM field
* Eligible grades
* Minimum age
* Maximum age
* Location
* Remote, in-person, or hybrid
* Cost category
* Cost amount
* Deadline
* Application opening date if known
* Experience level
* Time commitment
* Requirements
* Official URL
* Supporting source URLs
* Short summary
* Verification status
* Published status
* Last verified date

Use PostgreSQL if available in Replit.

Create 10 realistic sample opportunities for testing. Clearly label sample data so it is not mistaken for verified live information.

## Transparent Match Score

Calculate a match score out of 100 using fixed, explainable rules:

* Basic eligibility: 25 points
* STEM interest match: 20 points
* Opportunity type match: 15 points
* Location or format match: 10 points
* Cost preference match: 10 points
* Experience level match: 10 points
* Time commitment match: 5 points
* Deadline is open: 5 points

Display:

* Total match score
* Score breakdown
* Reasons the opportunity matches
* Reasons it may not match

Do not use an external AI model to calculate this score.

## Eligibility Checker

Return one of these labels:

* Eligible
* Maybe Eligible
* Not Eligible
* Deadline Passed

Check:

* Grade
* Age
* Location restrictions
* Experience requirement
* Deadline
* Remote or in-person availability

Show clear reasons for the result.

## Deadline Labels

Calculate these automatically:

* Apply Now: 7 days or fewer remaining
* Closing Soon: 8–30 days remaining
* Open: more than 30 days remaining
* Watchlist: application has not opened
* Closed: deadline has passed

Use the current date rather than hardcoded labels.

## Opportunity Results

Rank opportunities by match score.

Each result card should show:

* Opportunity name
* Organization
* Match score
* Eligibility label
* Deadline label
* Location or format
* Cost
* Short explanation
* Link to full details

Only show records where `published = true`.

## Opportunity Detail Page

Show:

* Full opportunity information
* Match-score explanation
* Eligibility explanation
* Deadline status
* Official application link
* Requirements checklist
* Verification status
* Last verified date

## Admin Dashboard

Create a private admin area that allows an administrator to:

* Add opportunities
* Edit opportunities
* Verify opportunities
* Publish or unpublish opportunities
* Review candidate opportunities
* Approve candidates
* Reject candidates
* Mark candidates as duplicates

Use a simple secure authentication method suitable for the MVP. Store credentials and secrets in Replit Secrets or environment variables. Do not hardcode passwords.

## Candidate Opportunity Review Queue

Create a separate candidate-opportunity table.

Candidate records may later be submitted by a Claude scheduled research agent.

Candidate fields should include:

* Name
* Organization
* Category
* STEM field
* Possible eligible grades
* Possible ages
* Location
* Format
* Possible cost
* Possible deadline
* Requirements
* Official URL
* Supporting source URLs
* Short summary
* Date discovered
* Review status
* Review notes

Review statuses:

* Needs Verification
* Approved
* Rejected
* Duplicate

Candidate records must never appear in public student results.

When a candidate is approved:

* Copy it into the main opportunities table
* Keep `published = false`
* Keep `verification_status = needs_verification`
* Require an administrator to verify and publish it separately

## Candidate Submission API

Create a protected API endpoint:

`POST /api/candidates`

Requirements:

* Authenticate using a bearer token stored in an environment variable
* Validate required fields
* Require an official URL
* Limit how many records can be submitted in one request
* Check duplicates using normalized official URL and program name
* Save only to the candidate table
* Always set `published = false`
* Always set review status to `Needs Verification`
* Return clear JSON success and error messages
* Add automated tests

Do not connect Claude or schedule daily research yet. Only prepare the secure endpoint and review queue.

## Safety and Data Rules

* Never publish automatically submitted opportunities
* Never treat Reddit or Quora as official verification
* Do not invent missing eligibility or deadline information
* Use `Unknown` for missing fields
* Clearly separate sample, candidate, verified, and published records
* Do not expose API tokens or admin credentials
* Do not commit `.env` files
* Validate all server-side inputs
* Sanitize displayed content

## Testing

Test the complete student workflow:

1. Open homepage
2. Complete matching form
3. View ranked results
4. Open an opportunity detail page
5. See score and eligibility explanations

Test the complete admin workflow:

1. Log in
2. Add or edit an opportunity
3. Publish and unpublish it
4. Review a candidate
5. Approve, reject, or mark it as duplicate
6. Confirm unpublished records remain hidden

Test the candidate API:

* Valid submission
* Missing token
* Invalid token
* Missing required fields
* Duplicate URL
* Duplicate program name
* Excessive batch size

## Design

Use a clean, modern, student-friendly design.

The interface should be:

* Responsive
* Accessible
* Easy to understand
* Appropriate for middle-school and high-school students
* Professional enough for a project demonstration

Prioritize usability over decorative animations.

## Do Not Build Yet

Do not build:

* Payments
* Paid subscriptions
* User accounts for students
* Email or text alerts
* Volunteer-hour tracking
* A chatbot
* OpenClaw integration
* Claude scheduled tasks
* Automated web research
* Automatic publishing
* STEM Voices videos
* FTC robot challenge functionality
* Personalized multi-year pathways
* Native mobile apps

## Development Process

Work in small milestones.

First create a `PLAN.md` file containing:

* Selected stack
* Database schema
* Page structure
* Milestones
* Files to create
* Testing plan
* Acceptance criteria

Then implement the project.

After implementation:

1. Install dependencies
2. Initialize the database
3. Add sample data
4. Run automated tests
5. Start the application
6. Fix errors
7. Provide the exact preview URL
8. Summarize all files created or changed
9. Explain how to configure required Replit Secrets
10. Explain how the future Claude scheduled research agent will connect to `/api/candidates`

Keep the solution simple, maintainable, and understandable to a student. Do not add unnecessary frameworks or services unless they clearly improve the MVP.
